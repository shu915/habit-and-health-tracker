# 認証とログイン

CLAUDE.md の「認証とデータの分離」の詳細。仕様を変えたら、ここも直す。

## 許可リスト(`ALLOWED_EMAILS`)
- 新規登録は、この許可リストの人だけ。**空のとき、開発は全員許可、本番は誰も許可しない**(`lib/allowlist.ts`)。許可外でも、画面の応答は同じにする(登録の有無を教えない)
- **確認する場所は 3 つ**: ユーザーを作るとき / ログインのメールを送る前 / **セッションを作るとき**(`lib/session-allowlist.ts`)。3 つ目は、マジックリンクも Google も、将来足すプロバイダーも、どの経路でも通る。理由: Google でのログインは、すでにいるユーザーとして入る(ユーザーを作らず、メールも送らない)ので、前の 2 つを通らず、許可リストから外した人が、連結済みの Google から入り直せた(2026-11-10 のレビューで発見)。判定の対象はアカウントのメール(`user.email`)で、連結した Google のアドレスは見ない
- **すでにあるセッションも、`getSession`(`lib/current-user.ts`)が、読むたびに許可リストを確かめて、外した人には null を返す**(セッションは使うたびに延びて、期限では切れないため。データを扱う関数も画面も、ここを通る)。許可リストが空のとき、本番は誰も許可しないので、設定を誤ると、全員が入れなくなる側に倒れる。`session` の行も消すのが望ましい(Better Auth 自身の API を、外した人が叩けなくなる)

## Google の連結とログイン
- **Google でログインできるのは、アカウントのページ(`/account`。ヘッダーのメールから)で連結した人だけ**。方針と守りは `lib/google-auth-options.ts`、テストは `google-auth.test.ts`(本物の Better Auth・メモリ上の DB・Google の通信だけ偽物)
  - Google だけではユーザーを作れない(`disableSignUp`)
  - メールが一致しても、勝手に連結しない(`disableImplicitLinking`)。**外さない**。メールが確認済みでないプロバイダーがあるため。`trustedProviders` にも、メールを確認しないプロバイダー(LINE など)を入れない
  - Google のメールは、アカウントのメールと違ってよい(ログイン中の本人だけが連結できるため。`allowDifferentEmails`)
  - 連結・解除は、5 分以内にログインした人だけ(`session.freshAge`)。連結したら、本人のメールに知らせる
  - 解除しても、マジックリンクで入れる。トークンは暗号化して保存する(`encryptOAuthTokens`)
- GitHub や LINE を足すときも、同じ形にする
- 開発で、スマホ(192.168.x.x)から Google は使えない(Google が、プライベート IP のリダイレクトを許さない)。メールのリンクで入る
- 画面: アカウントのページは、状態のタグ(連結済み・未連結)と、操作のボタン(連結する・解除する)を、**別の形にする**(混同されるため)。エラーは、行の下の全幅に出す(`docs/screens.md`)

## ログインのメール(マジックリンク)
- 送るのは `lib/email.ts`。**開発・テストはコンソールに出し**(リンクは `next dev` の端末に出る)、**本番は Resend の REST API**で送る(`RESEND_API_KEY`・`MAIL_FROM` が必須。無ければエラー。`MAIL_REPLY_TO` は任意)。`EMAIL_TRANSPORT=resend` で、開発でも実際に送れる。文面は `lib/login-email.ts`
- **本番では、宛先・本文(ログインリンク)をログに出さない**。送信に失敗しても、画面には「送信しました」と出る(同じ応答)ので、失敗はログの `[email] failed` で見る
- **回数の制限は 2 段**: IP 単位(Better Auth)と、**メールアドレス単位**(10 分に 3 回・1 日に 10 回。`lib/login-rate-limit.ts`)。アドレス単位は、IP を変えながら友人の受信箱を荒らされるのを止める。許可リストの内外を問わず、同じ判定・同じ応答 429(内の人にだけ「多すぎる」と返すと、登録の有無が分かるため)。**断った要求は記録しない**(断られ続けても、解除が延びない)。アドレスは SHA-256 のハッシュで持ち(`login_link_requests`。`user_id` を持たない、唯一の表)、「数える → 足す」はアドレス単位のロックで直列にする。開発は上限なし
- **許容している制約**: 他人が友人のアドレスに、10 分に 3 回送り続けると、その友人は、その間、ログインのメールを依頼できない(登録の有無を教えない仕様との引き換え)
- **IP 単位の制限が読むヘッダー**(`lib/auth-options.ts` の `IP_ADDRESS_HEADERS`): `x-vercel-forwarded-for`(Vercel が接続元だけを入れる)→ `x-forwarded-for`。指定が無いと、Better Auth は `x-forwarded-for` が 1 つの値のときだけ IP を採用し、複数の値(手前に Cloudflare などのプロキシがある)だと採用せず、**全員が 1 つの枠(`no-trusted-ip`)を共有する**。外から 1 分に数回叩くだけで、全員のログインと、リンクを開く操作が止まる。デプロイ後に、実際に取れているかを確かめる(`docs/release-checklist.md`)
- **設定の配線**は `lib/auth-options.ts` の `createAuthOptions` にあり、本番(`auth.ts`)とテスト(`auth-options.test.ts`・`google-auth.test.ts`)が同じ関数を使う。差し替えるのは、DB・メールの送信・アドレス単位の制限・プロフィールの作成だけ。配線の行を消すと、テストが落ちる

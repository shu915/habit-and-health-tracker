# データの規則

CLAUDE.md から分けた詳細。仕様を変えたら、ここも直す。

## データの規則
- 値の範囲は `lib/*-limits.ts` に集約する(`app` = zod とフォームの現実的な範囲、`db` = CHECK 制約の広い範囲)。**app は db の内側**(テストで守る)。CHECK の SQL は `schema.ts` に直接書くので、db の範囲を変えるときは、定数・`schema.ts`・マイグレーションを一緒に直す
- 保存は「入力に**あった項目だけ**」を更新する(キーが無い項目は変更せず、空欄は null で空にする)。フォームに項目を足したら、`*-schema.ts` と `*-form.tsx` の両方に足す
- 個人の値は null が「未入力」。使う側で「未設定」として扱う。活動係数は 5 つの選択肢だけ
- フォームの検証は zod。数値は文字列の正規表現で先に絞る(zod の変換は `0x10` や `1e2` を通すため)。**zod をブラウザ側のコードに入れない**(クライアントのフォームは `*-schema` を type import だけで読む)
- 睡眠は `days` の `sleep_bedtime`(前の夜)と `sleep_wake_time`(今朝)の 2 列で、**起きた日**に入れる。睡眠時間は保存せず、2 つの時刻から計算する。昼寝や夜中に起きた記録は扱わない
- 測定値(体重・体脂肪率)の列には、測った値だけを入れる。式で見積もった値は入れない

### その日の値の固定(過去の日を今のプロフィールで書き換えない)
- **目標カロリーと活動係数は、日の行に写して固定する**(`days.profile_target_calories` / `profile_activity_level`)。日の行を**初めて作るとき**に写し(`insertDayIfMissing`。日の行を作る所は必ずここを通す)、更新では書き換えない。過ぎた日は、あとでプロフィールを直しても当時のまま(手で直す画面は作らない。割り切り)
- **例外**: 書きかけの日(今の食事の日とそれより先。`isFinishedDay` が false)は、プロフィールの目標カロリーか活動係数を保存したときに、写しも新しい値にそろえる(`updateProfile`。今日の目標を昼に直しても夜まで朝の値で比べられるのを防ぐ)
- 写しが null なら、読む側が今のプロフィールで補う(安全網)。読むのは `getDayBasis`(`lib/days.ts`): 体重・体脂肪率・この 2 つをその日の値に差し替えたプロフィールを返す
- **体重・体脂肪率**は、その日の朝の値 → それ以前の最新の朝の値 → プロフィール(`pickWeight` / `pickMeasure`)。朝の値は手で入れるので、これが「その日のスタンプ」で、直せばその日の数字も更新される。年齢・身長は固定しない(影響が小さい)。ダッシュボードの「消費カロリーの目安」は今のプロフィールのまま(現在の値を見るカード)
- **空のまま保存しても日の行は作らない**(`saveDayUnlessEmpty`。作ると、その時点の目標が固まるため)。食事・運動・良かったことは中身があるときだけ作る
- **記録を始めるには、プロフィールの目標カロリーと活動係数が必要**(`isProfileReady`、`requireRecordingProfile`): 未設定で日の行を作ると写しが空になるため。**画面側で塞ぐ**(`lib/recording-gate.ts`): その日の行がまだ無く、未設定のときだけ。日の行を作る 5 つの画面(朝の記録・食事の追加・運動の追加・良かったこと・今日の気づき)と、その保存の Server Action が `/profile/edit` へ送る。行がすでにある日、閲覧、既存の食事/運動の編集と削除は塞がない。プロフィール保存後は元の画面へ戻らず `/` へ行く(`?next=` で戻す案は、オープンリダイレクトの穴になるので見送った)。**保存関数(`saveDay` など)は塞がない**(テストが多く壊れるため)ので、新しい「日を作る」画面を足したら、同じ確認を入れる

# 公開前に決めること

CLAUDE.md から分けた詳細。仕様を変えたら、ここも直す。

## 公開前に決めること
- **ログインまわりのセキュリティ(デプロイ後に確かめる)**: ① **プロキシ越しの IP の取り方**。`lib/auth-options.ts` で、`x-vercel-forwarded-for` → `x-forwarded-for` の順に読むよう指定してある(Vercel が接続元だけを入れるヘッダー。**名前と挙動は、Vercel の資料で確かめる**)。IP が取れないと、IP 単位の制限が、**全員で 1 つの枠(`no-trusted-ip`)**になり、外から 1 分に数回叩くだけで、全員のログインと、リンクを開く操作が止まる。**確かめ方**: ログインのメールを 1 回依頼したあと、Neon の SQL エディタで `SELECT key FROM rate_limit;` を見て、鍵が `<あなたのグローバル IP>|/sign-in/magic-link` の形なら合格(`no-trusted-ip` なら、取れていない)。Vercel のログに `Rate limiting could not determine a client IP` の警告が出ていないかも見る。別のネットワーク(スマホの回線など)から依頼して、別の鍵ができることも確かめる(メールアドレス単位の制限は、IP に頼らず、実装済み。**許容している制約**: 他人が友人のアドレスに、10 分に 3 回送り続けると、その友人は、その間、ログインのメールを依頼できない。登録の有無を教えない仕様との引き換え。a+1@… のようなエイリアスは、別のアドレスとして数えるが、許可リストは完全一致なので、許可の外には、そもそも送らない)。**デプロイでは、マイグレーションを先に当てる**(login_link_requests の表が無いと、ログインのメールの依頼が、500 になる)② リンクスキャナ(メールのセキュリティ機能がリンクを先に開き、1 回しか使えないログインリンクを消費してしまう問題)は、起きたら対処する ③ **メールの送信に失敗しても、画面には「送信しました」と出る**(登録の有無を教えないための、同じ応答)。デプロイ後に、自分でログインを 1 回試し、届かなければ、Vercel のログで `[email] failed` を探す(Resend のキーの期限切れ、ドメインの認証切れ、無料枠の超過が、ここに出る)。Vercel のアクセスログに、ログインリンクの文字列(1 回使うと無効、5 分で期限切れ)が出ていないかも見る
- **Google でのログイン(デプロイ時)**: Vercel の環境変数に `GOOGLE_CLIENT_ID` と `GOOGLE_CLIENT_SECRET`、`BETTER_AUTH_URL`(`https://hht.shu-digital-works.com`)を入れる。Google Cloud の OAuth クライアントの承認済みのリダイレクト URI に、`https://hht.shu-digital-works.com/api/auth/callback/google` が入っていること(入力済み)。同意画面が「テスト」なら、使う友人のアドレスを「テストユーザー」に入れる(`openid`・`email`・`profile` だけなら、公開にしても審査は要らない)。デプロイ後に、アカウントのページで連結し、ログアウトして、Google でログインできるか確かめる(最初の 1 回は、必ずメールのリンクで入る)。開発で、スマホ(192.168.x.x)から Google は使えない(Google が、プライベート IP のリダイレクトを許さない)ので、スマホはメールのリンクで
- **マイグレーションを当てたあと、本番の DB に当たったことを確かめる**: `drizzle.config.ts` は、`DATABASE_URL` が無いと、開発用 DB に黙って当たる(成功の表示が出る)。付け忘れの事故を防ぐため、適用のあと、本番の SQL エディタで `SELECT count(*) FROM drizzle.__drizzle_migrations;` が **10** になっていることを確かめる。接続は、アプリの実行時は **pooled**(`-pooler`)、マイグレーションは **direct** を使う(トランザクション内のロックは、pooled でも動く)
- **デプロイ時に、Neon の DB のタイムゾーンが UTC か確かめる**(`SHOW timezone`)。1 日の回数制限の 03:00 区切り(`lib/meal-day-sql.ts`)が、`created_at` を UTC の壁時計として比べるため、違うと区切りが 9 時間ずれる。アプリの時計は日本時間に固定済み(`lib/time-zone.ts`。規則は CLAUDE.md)。接続の設定で UTC に固定する手(`options=-c timezone=UTC`)は、Neon のプールされた接続が受け付けないことがあるので使わない

## デプロイ後にやること
- **レポートの作成にかかる時間を測って、`maxDuration` を決める**: 食事の推定は最悪約 70 秒(食事の追加・編集のページに `maxDuration = 90` を置いてある。Vercel の Fluid compute が有効なら、既定でも足りる)、レポートの作成は返事を返したあと裏(`after`)で AI を呼び続けて約 4 分、**長期レポートを初めて作るときは最悪約 8 分**(月ごとのテーマ約 4 分 + 本体約 4 分)の見込み。`reports/page.tsx` に `maxDuration = 300` を置いてあるが、実際の所要時間は手元では測れない。①使う Vercel のプランの上限を、公式の説明で確かめる ②「ページの設定が、そのページから呼ばれる Server Action にも効くか」を確かめる ③月次・四半期・年次(初めて)を作って、実際の所要時間を見て、`maxDuration` を決める。上限を超えると、作成中のまま止まり、6 分(長期は 12 分)後に失敗になる(データは壊れない。月ごとのテーマは 1 か月ずつ保存されるので、押し直せば続きから進む)。足りなければ、長期レポートの作成を「テーマ作り」と「本体」の 2 回に分ける、またはテーマの並行数(今は 3)を増やす
- **データのバックアップ**: 本番の DB は Neon。無料枠の履歴(PITR)は 6 時間だけで、定期のバックアップは無い。**GitHub Actions で毎晩 `pg_dump` を取り、Cloudflare R2(S3 互換。無料枠で足りる見込み)に置く**(`pg_dump` はサーバーレス関数では動かないので、Actions で実行する)。バケットは非公開にし、古い dump は自動で消す設定にする(健康情報なので、保存先の公開設定と保持期間を決める。暗号化するかも決める)。**復元の練習を 1 回やる**(取れていても、戻せなければ意味がない)。**退会した人(`user` の行を消した人)のデータは、ダンプには残る**ので、保持期間を決めたら、「退会してから消えるまでの日数」として、友人に伝える

- **応答ヘッダー**: `X-Frame-Options: DENY`・`X-Content-Type-Options: nosniff`・`Referrer-Policy: same-origin` を付けてある(`next.config.ts`)。Cookie の属性(`SameSite=Lax`、`Secure`、`HttpOnly`)は、Better Auth の既定のままなので、デプロイ後に、ブラウザの開発者ツールで確かめる

## 作らないと決めたこと(友人が少ないため。理由つき)
- プライバシーと利用規約のページ: 友人には口頭で伝える(AI の提供元にデータが送られることは、同意の画面に出している)
- 退会の機能: 必要なら、DB から `user` の行を消す(`cascade` で全部消える)
- 全ユーザー合計の AI の費用の上限: OpenRouter のキーに、月の上限を付ける
- 長期レポートの 1 日の回数の上限と、「失敗を数える」仕組み: 失敗後 10 分の待ちだけある(`docs/ai-feedback.md`)
- ログインのリンクが期限切れ・使用済みのときの専用の画面: 標準の表示のまま
- ヘッダーとナビの 375px の確認: 実機で確認済み
- **公開後に列を削除するとき**: コードを先に出し、列の削除は次のリリースに分ける(先に DB を変えると、古いコードが「列が無い」で全ページ 500 になる)

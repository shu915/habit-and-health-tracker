# 公開前に決めること

CLAUDE.md から分けた詳細。仕様を変えたら、ここも直す。

## 公開前に決めること
- **ログインまわりのセキュリティ(デプロイ後に確かめる)**: ① プロキシ越しの IP の取り方(Better Auth の `advanced.ipAddress` の `ipAddressHeaders` と `trustedProxies`)。Vercel の裏で IP が正しく取れないと、ログインのレート制限が、全員を同じ IP と見て全員を止めたり、効かなくなったりする。デプロイ後に、数回ログインを試して確かめる ② リンクスキャナ(メールのセキュリティ機能がリンクを先に開き、1 回しか使えないログインリンクを消費してしまう問題)は、起きたら対処する (本番のメール送信は、宛先とリンクをログに出さない。実装済み・テスト済み)
- **デプロイ時に、Neon の DB のタイムゾーンが UTC か確かめる**(`SHOW timezone`)。1 日の回数制限の 03:00 区切り(`lib/meal-day-sql.ts`)が、`created_at` を UTC の壁時計として比べるため、違うと区切りが 9 時間ずれる。アプリの時計は日本時間に固定済み(`lib/time-zone.ts`。規則は CLAUDE.md)。接続の設定で UTC に固定する手(`options=-c timezone=UTC`)は、Neon のプールされた接続が受け付けないことがあるので使わない

## デプロイ後にやること
- **レポートの作成にかかる時間を測って、`maxDuration` を決める**: 食事の推定は最悪約 70 秒、レポートの作成は返事を返したあと裏(`after`)で AI を呼び続けて約 4 分、**長期レポートを初めて作るときは最悪約 8 分**(月ごとのテーマ約 4 分 + 本体約 4 分)の見込み。`reports/page.tsx` に `maxDuration = 300` を置いてあるが、実際の所要時間は手元では測れない。①使う Vercel のプランの上限を、公式の説明で確かめる ②「ページの設定が、そのページから呼ばれる Server Action にも効くか」を確かめる ③月次・四半期・年次(初めて)を作って、実際の所要時間を見て、`maxDuration` を決める。上限を超えると、作成中のまま止まり、6 分(長期は 12 分)後に失敗になる(データは壊れない。月ごとのテーマは 1 か月ずつ保存されるので、押し直せば続きから進む)。足りなければ、長期レポートの作成を「テーマ作り」と「本体」の 2 回に分ける、またはテーマの並行数(今は 3)を増やす
- **データのバックアップ**: 本番の DB は Neon。無料枠の履歴(PITR)は 6 時間だけで、定期のバックアップは無い。**GitHub Actions で毎晩 `pg_dump` を取り、Cloudflare R2(S3 互換。無料枠で足りる見込み)に置く**(`pg_dump` はサーバーレス関数では動かないので、Actions で実行する)。バケットは非公開にし、古い dump は自動で消す設定にする(健康情報なので、保存先の公開設定と保持期間を決める。暗号化するかも決める)。**復元の練習を 1 回やる**(取れていても、戻せなければ意味がない)

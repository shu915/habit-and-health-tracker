# 公開前に決めること

CLAUDE.md から分けた詳細。仕様を変えたら、ここも直す。

## 公開前に決めること
- 決定済み(実装はこれから): メール送信は **Resend**(`lib/email.ts` の本番側)/ デプロイ先は **Vercel**(アプリ)と **Neon**(DB)。秘密情報は Vercel の環境変数に置き、`BETTER_AUTH_URL` は https にする / 睡眠データは手入力(インポートは作らない)
- **マイグレーションの運用(公開後)**: 列の削除は元に戻せず、先にマイグレーションを当てると旧コードが「列が無い」エラーで全ページ 500 になる(Drizzle は全列を select する)。コードを先に出して、列の削除は次のリリースに分ける
- embedding を使うときは、新しいマイグレーションで `CREATE EXTENSION vector` を足し、Docker と CI のイメージを pgvector 入り(`pgvector/pgvector:pg17`)に戻し、Neon で使えることを確かめる(次元数は列定義に影響し、インデックスは 2000 次元まで)
- **日付の境目はサーバーの日付**: `isFinishedDay`、`updateProfile` の書きかけの日の写し直し、`defaultMealDayAndTime`、月末のウエストの帯。サーバーが UTC だと、日本時間の 03:00〜12:00 は、サーバーから見て昨日がまだ書きかけで、この時間帯にプロフィールの目標を直すと昨日の写しまで上書きされる(履歴が静かに変わる)。デプロイ時に、利用者のタイムゾーンで判定するか決める
- デプロイ時: 食事の推定の Server Action の実行時間の上限(`maxDuration`。呼び直しを含め最悪約 70 秒。写真 4 枚の実測は無く、ログの秒数で見直す)/ プロキシ越しの IP の取り方(`advanced.ipAddress` の `ipAddressHeaders` と `trustedProxies`)、メールアドレス単位の送信回数の制限、期限切れの `verification` 行の掃除、リンクスキャナにトークンが先に消費される問題、IP・User-Agent の保持期間
- 食事の内容と写真は OpenRouter 経由でモデルの提供元に送られる。`data_collection: "deny"` で制限しているが、提供元ごとの保持・学習の扱いを、公開前に利用規約で確認し、友人にも伝える。本番のログには入力の内容を残さない
- 健康情報は平文で保存している。公開前に、バックアップとログに出る範囲、退会時の cascade の範囲を確認する
- 今は許容: 別タブでプロフィールの目標を空にした直後に食事の推定から保存すると、`/profile/edit` へ送られ推定結果が消える / 同時編集は最後の保存が勝つ / 1 日の食事の件数に上限がない(付けるなら運動と同じく、その日の行のロックで数える)/ 保存の二重送信はサーバー側で防いでいない(重複は削除できる)
